# EasyTravel 平台化升级指导书

> 版本：v1.1 · 编写时间：2026-11-11（同日完成第二轮遗留清理，见第 8 节）
> 适用代码基线：`main` 分支，**184 个后端测试 + 9 个前端单测**全绿，离线评测 mean = 72.3，`pip-audit` 0 漏洞
> 本文件用途：**当决定把 EasyTravel 从"个人本地工具"升级为"旅游规划平台"时，按本文档逐阶段执行。**
> 不升级时，本文件不需要做任何事。

---

## 0. 先读这一节：什么时候该执行，什么时候不该

### 应该启动的信号（满足任意两条）

- 有 **10 个以上陌生人**在持续使用，且你开始收到"想分享给别人"的请求
- 有人愿意**付钱**（哪怕只是 9.9 元）
- 你发现自己在手工为别人生成行程
- 你希望看到留存、复购、转化这类数字

### 不该启动的信号（满足任意一条就再等等）

- 使用者仍然基本是你自己
- 你还没想清楚"谁为什么付费"
- 你只是觉得"平台听起来更高级"

**技术债不是升级的理由。** 现在这套代码的清晰度是它最大的资产——7k 行、一个人能装进脑子、171→179 个测试全绿。过早平台化会用这份资产换一堆运维复杂度，而换来的东西大概率用不上。

### 一个必须先做的判断

平台化不是"加中间件"，是**四个底层假设同时翻转**：

| 假设 | 现状 | 平台化后 |
|---|---|---|
| 谁在请求 | 匿名、客户端自报 | 真实账号 + 会话 |
| 数据量级 | 一个人的几十份行程 | 百万级、多租户、要分页与归档 |
| 谁付钱 | 用户自带 Key | 平台垫付，必须计量与计费 |
| 任务时长 | 请求内跑完 30–70s | 必须异步、可恢复、可观测 |

**四条里只要有一条不翻，就别进阶段 0。** 尤其第三条——只要你还是"用户自带 Key"，就不需要计费、不需要配额、不需要 Redis 计数。

## 1. 当前架构快照（升级前的基线，用于对比）

| 层 | 现状 | 平台级瓶颈 | 位置 |
|---|---|---|---|
| 进程模型 | FastAPI 单进程，`--workers>1` 会锁库 | **硬阻塞**：无法水平扩容 | `README` 常见问题 |
| 存储 | SQLite 单文件，plan 存 TEXT | 并发写、多副本、无法查询 | `src/service/database.py` |
| Schema 演进 | 手写 `ALTER TABLE` | 第二次改表就出事 | `database.py:47` |
| 身份 | 匿名 `X-Client-Id`，缺省落 `local` | 无法承载计费与账号 | `src/api/security.py` |
| 成本保护 | 进程内 dict + `asyncio.Semaphore` | 多副本各算各的 | `src/service/generation_guard.py` |
| 候选缓存 | 进程内 `TTLCache` | 多副本不共享，重复打供应商 API | `src/service/cache.py` |

| 评测 | 24 case + 确定性指标（已修正） | 无门槛、judge 自评 | `evals/` |

**可以直接带到平台的资产（不要重写）**：`planning/scheduler.py`、`planning/critic.py`、`planning/llm_planner.py`、`planning/plan_editor.py`、`service/llm_gateway.py`、`service/llm.py`、`model/schemas.py`。

## 2. 阶段总览与门禁

```
Gate 0 ──> 阶段 0（能收钱，约 2 个月）──> Gate 1 ──> 阶段 1（能撑住，2–6 月）──> Gate 2 ──> 阶段 2（能扩展，6–12 月）
```

| Gate | 判据（全部满足才进下一阶段） |
|---|---|
| **Gate 0** | 有付费意愿证据；地图数据合规问题已书面确认 |
| **Gate 1** | 陌生人能注册→付费→生成→拿到结果；服务重启不丢任务；单次成本可核算 |
| **Gate 2** | 1 万 DAU 下 P95 < 60s；单次成本较阶段 0 下降 ≥ 30%；评测有阈值门禁 |
| **Gate 3** | 生成域与检索域可独立扩缩容；多端接入不互相阻塞 |

**每个阶段结束必须能回退到"本地工具"模式**（见第 7 节）。

## 3. 阶段 0：能收钱（最高优先级）

> 目标：一个陌生人能注册、付费、生成、拿到结果，且服务重启不丢任务。
> 预估：单人 6–8 周。

### 0.1 真实身份（决定后面一切）

- **改动**：`src/api/security.py` → 新增 `src/api/auth.py`（Authlib + JWT access/refresh）；`routes.py` 的 `Depends(get_owner_id)` 改为 `Depends(current_user)`
- **保留游客态**：未登录可生成 1 次（用一个 HttpOnly cookie 记游客桶），登录后把游客桶的计划一次性 claim 到账号
- **数据迁移**：`owner_id`（TEXT）→ `user_id`（FK → `users.id`）；新增 `users`、`sessions` 表
- **撤销**：本地版的 `local` 桶降级为"游客桶"，语义不变
- **验收**：两个账号互查均为 404（现有 `test_ownership.py` 改造成账号维度）；token 过期返回 401 且 refresh 可用

### 0.2 存储换 PostgreSQL

- **改动**：`src/service/database.py` → 引入 SQLAlchemy 2.0 async + `asyncpg`；新增 `alembic/`
- **关键决策**：`plan_json` 存 **JSONB**，不要拆成关系表。行程是"一次写入、整份读取"的文档，拆表只会让你为查询写一堆 join，却没有真实收益
- **一次性导入脚本**：`scripts/import_sqlite.py`，把旧库读出来写进 Postgres
- **验收**：`alembic upgrade head` 在空库一次成功；`alembic downgrade -1` 可回退；旧库导入后行程数对得上

### 0.3 成本保护搬进 Redis（**保留退款语义**）

- **改动**：`src/service/generation_guard.py` → Redis 实现
- **语义必须保留**（这是本地版已经修好的，不要丢）：
  - 成功才计数：失败/中断要 `DECR` 退回
  - 被"机器忙"拒绝**不能**扣次数
  - 每日计数用 `INCR quota:{user_id}:{yyyymmdd}` + `EXPIREAT` 到当日结束
- **验收**：起**两个** API 副本，从副本 A 计数、在副本 B 上必须看到同一个数（这条测试本地版无法写，平台版必须写）

### 0.4 长任务出进程

- **改动**：`routes.py:100` 的 `produce()` 移出；新增 `worker/` 进程（**Arq**）
- **接口契约翻转**（这是阶段 0 最大的工作量）：

```
POST /api/trip/plan            -> 202 {"task_id": "..."}      # 不再等结果
GET  /api/trip/plans/{id}/events  -> SSE 订阅（可重复订阅、可重连）
GET  /api/trip/plans/{task_id}    -> 轮询兜底（给不支持 SSE 的端）
```

- **SSE 必须换成 Redis Stream**：`routes.py:94` 的 `asyncio.Queue` 是**多副本第一个硬阻塞点**。请求落在副本 A、任务跑在副本 B 时，现在的实现直接断流
- **验收**：提交任务后立即刷新页面，重新订阅能拿到完整进度；杀掉的 worker 不产生孤儿 running 任务

### 0.5 接上 LangGraph checkpointer（**性价比最高的一刀**）

- **改动**：`src/agent/trip_planning_graph.py:84`

```python
# 现在
return builder.compile()

# 改后
return builder.compile(checkpointer=PostgresSaver.from_conn_string(...))

# run() 里
state = await self.graph.ainvoke(
    {"request": request, "revision": 0, "on_event": on_event},
    config={"configurable": {"thread_id": task_id}},
)
```

- **收益**：worker 崩溃/重启后从断点续跑，**不重跑已经付费的 LLM 与高德调用**；顺带获得完整的执行回放能力
- **成本**：约 20 行。你已经依赖 `langgraph==1.2.10`，能力躺在依赖里没用
- **为什么不用 Temporal**：见 ADR-3

### 0.6 计费

- **新增表**：`plans`（套餐）、`orders`、`ledger`（流水，只追加不改）
- **原子性**：生成前预扣额度 → 成功确认 → 失败退还。与 0.3 的退款语义合并实现
- **对账**：每日对账任务，比对 `ledger` 与实际模型调用账单
- **验收**：并发 10 个生成请求，额度不会被超扣；失败全部退还

### 0.7 限流上移到网关

- **改动**：Nginx / Traefik 按 IP + 按 user 双维度限流
- **同时删除**：应用层的限流（多副本下本来就不准，留着是误导）
- **验收**：单 IP 超过阈值返回 429 且带 `Retry-After`

## 4. 阶段 1：能撑住

> 目标：1 万 DAU 稳定，单次成本可核算并下降 ≥ 30%。

### 1.1 前后端分离 + 对象存储

- 前端独立部署到 CDN；`main.py:85` 的 `_mount_frontend()` 删除
- PDF 改为**服务端生成**（`weasyprint` 或 Playwright 打印）→ 存 S3/OSS → 返回带签名的可分享链接
- 顺带修掉前端三个 P0（见第 8 节遗留清单）

### 1.2 可观测

- OpenTelemetry：`web` / `worker` / `llm` / `amap` 四类 span；`/metrics` 暴露 Prometheus
- **Langfuse** 接 LLM 网关：trace、token、成本、prompt 版本 ↔ 质量关联
- 关键看板：单行程成本、P50/P95 延迟、降级率、缓存命中率、judge 分数分布

### 1.3 缓存分层

| 层 | 内容 | TTL |
|---|---|---|
| 结果缓存 | `hash(city, prefs, budget, days, accommodation)` → 整份 plan | 6–24h（同城同偏好直接用） |
| 供应商缓存 | POI / 路线 / 天气 → Redis | 10min–7d |
| 前缀缓存 | 模型 system prompt + 候选列表 | 由供应商前缀缓存自动生效 |

**注意**：结果缓存命中时要明确标注"复用"，否则用户会以为行程是为他现算的。

### 1.4 模型路由与成本

- `ModelProfile` 增加 `role` 字段：`planner` / `reviser` / `judge` / `cheap`
- `LLMGateway` 按 role 选链：判断类用小模型，规划类用大模型
- **prompt 前缀稳定化**：候选列表顺序不要每次随机，否则前缀缓存永远不命中（现在是按高德返回序，天然稳定——别在重构时打乱）
- 成本公式（用于估算，替换成你的真实价格）：

```
月成本 ≈ DAU × 人均生成次数 × 30 × (in_tok × Pin + out_tok × Pout) + 供应商 API + 基础设施
算例：DAU 1000 × 2 次 × 30 天 × (800×Pin + 5000×Pout)
```

### 1.5 检索

- 把高德 POI 落库成**自建 POI 库**（Postgres + Meilisearch），减少对单次搜索的依赖
- **合规前置**：见第 6 节，确认条款允许存储与展示后再做，否则此步作废

### 1.6 评测闭环（本地版的欠账，这里补上）

- judge 换成**独立模型**（不能与 planner 同一条 chain）
- 人工标注 20–30 条作为校准集，要求 judge 与人工 Spearman ≥ 0.6
- CI 加**阈值门禁**：离线基线不得低于 72.0；live 不得低于离线 + 5；降级率不得高于 10%
- 现在 `evals/__main__.py` 恒定返回 0，这条不改，评测就没有牙齿

## 5. 阶段 2：能扩展

> 目标：只拆两个域，其余保持单体。

### 2.1 只拆两个服务

| 服务 | 职责 | 理由 |
|---|---|---|
| `generation-service` | LangGraph 编排、LLM 调用 | 消耗模型算力，扩缩容曲线与检索完全不同 |
| `search-service` | POI 检索、路线、天气聚合 | 高 QPS、低延迟、可重度缓存 |
| 其余 | 账号、计费、行程读写、导出 | **继续保持单体** |

**明确反对**：不要按"前端/后端/用户/订单"拆成六七个服务。你没有那种组织规模，拆完只会得到一个分布式单体 + 一份运维噩梦。

### 2.2 攻略 RAG

- pgvector 存用户上传的攻略/游记切块
- 入口："按这篇攻略帮我排 3 天"
- 注意 prompt injection：攻略是**不可信输入**，只能作为检索上下文，绝不能当指令

### 2.3 多端

- 小程序/App 通过 BFF 层接入，复用同一套 API
- 移动端优先改 SSE 为 WebSocket 或长轮询

## 6. 不能忘的两条红线（比技术选型更致命）

### 6.1 地图数据合规 —— **在写第一行平台代码之前确认**

现状：把高德 POI 存进 SQLite 再对外展示。**个人本地使用没问题；ToC 平台公开再分发可能违反服务条款。**

必须先书面确认：
1. 是否允许**落库**（持久化存储）
2. 允许的**缓存时长**
3. 是否允许**二次展示**给其他用户
4. 是否需要**测绘资质**（导航类服务）

**降级方案**（如果条款不允许）：只存 `poi_id` + 自己计算的派生字段（距离、排序分），原文按次实时取、不落库。这会让 1.5 的自建 POI 库作废，所以这条必须最先确认。

### 6.2 LLM 成本就是 COGS

以当前 token 消耗（600–1000 in + 3000–7000 out）计，DAU 1000 × 2 次/天 ≈ 每日 4000 万–1.4 亿 output token。**毛利完全由这一项决定**，而它只受四件事影响：

1. prompt caching（前缀复用）
2. 小模型路由（判断类下沉）
3. 结果缓存命中率
4. 思考预算分级（`LLM_REASONING_EFFORT`，本地版已做）

任何产品功能提案，如果会显著增加"每单模型调用次数"，都应该按成本否决或重新设计。

## 7. 回滚策略

每个阶段都必须能回到"本地工具"：

- 配置开关 `PLATFORM_MODE=false` → 走 SQLite + 进程内计数 + 同步生成
- **SQLite 双写保留 3 个月**（阶段 0 期间），确认无问题再撤
- 每个阶段一个独立分支 + 一个 tag，回滚 = 切 tag + 反向 alembic
- 灰度：先给 5% 新用户走新链路，观察降级率与 P95 再放量

## 附录 A：架构决策记录（ADR）

### ADR-1 任务队列用 Arq，不用 Celery

现有全部代码是 async（`httpx`、`AsyncOpenAI`、LangGraph）。Celery 是同步生态，接进来要重写一遍 I/O 层。Arq 基于 Redis、asyncio 原生，最小改动。只有在出现大量同步/CPU 密集任务时才重新评估。

### ADR-2 先不上 Kubernetes

Postgres + Redis + Arq + 现有单体，足够撑到几万 DAU。过早拆分会毁掉"7k 行、一个人能装进脑子"这个最大资产。**先上 K8s 的人，通常是在解决自己制造的容量问题。**

### ADR-3 用 LangGraph checkpointer，不用 Temporal

任务形态是"单条有向流水线 + 少量条件回边"，不是复杂 saga。LangGraph 已内置 Postgres/SQLite checkpointer，而且已经在依赖里。引入 Temporal 需要重写编排层，收益不匹配。**只有当出现"跨天等待人工确认""多服务补偿事务"时才重新评估。**

### ADR-4 行程存 JSONB，不拆关系表

行程是"一次写入、整份读取"的文档型数据。拆成 `days`/`attractions`/`meals` 三张表，只会为统计需求写一堆 join，而统计需求用 JSONB 的 GIN 索引足够覆盖。**只有在需要"按景点反查去过的人"这类图查询时才拆。**

### ADR-5 保留 `planning/` 的确定性核心，不交给模型

`optimise_order`、`pick_meals`、`PlanCritic` 是这套系统可信度的来源。平台化会让人想"把排程也交给更强的模型"，**不要**。模型只决定"去哪几个"，几何与预算必须保持确定性——这是本项目的核心设计承诺，也是成本控制手段。

### ADR-6 评测的偏好在 `name + category` 上算，不看 `description`

`description` 是模型（或模板）写的散文，用它算偏好匹配度等于在衡量"作者会不会复述需求"。2026-11 已修复此缺陷（修复前离线基线 85.9，修复后 72.3）。平台化新增任何文本类指标时，同理不要对模型自己写的字段做自评分。
